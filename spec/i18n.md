# i18n contract

Three locales: `en_us`, `zh_cn`, `zh_tw`. Today they live in `src/i18n/*.xml`,
are converted to TypeScript by a generator (`src/i18n/xml-to-ts.js`), and are
protected by hash baselines (`src/test/i18n-*.json`) plus a preservation
projection that needs a named exception per additive attribute. That machinery
costs a round every time a user-visible string or a dialog attribute changes.

## Target

```
src/lib/i18n/
  locales/en_us.ts     // the reference locale; its type defines every key
  locales/zh_cn.ts
  locales/zh_tw.ts
  index.ts             // useT(), t(key, vars), fallback rules
  parity.test.ts       // the contract, executable
```

- Keys stay **exactly** the ones shipped today. This is a structural change, not a
  copy change: no user-visible string may alter in the port, and the parity test
  compares against a frozen snapshot of the current XML output to prove it.
- `en_us` is the type source. `zh_cn` and `zh_tw` are typed as the same shape, so a
  missing or extra key is a compile error, not a runtime blank.
- Interpolation is `{name}` placeholders through one `t()` implementation. No
  component builds a sentence by concatenating translated fragments.
- Locale choice is a device preference (`app-language`), read by `lib/i18n` only.
  Switching locale is a state change, not a reload, and never resets scroll or the
  open dialog.

## The contract (what `parity.test.ts` enforces)

1. The three locale modules expose an identical key set — missing and extra keys
   both fail, with the key path in the message.
2. The same placeholder set appears in every locale for a given key.
3. No CJK characters in `en_us`; no untranslated `en_us` value in a CJK locale
   unless the string is a proper noun (a short allowlist in the test).
4. No user-visible string literal in `src/features` or `src/ui`: the existing
   hardcoded-copy test moves here unchanged, because it is the rule that caught
   real defects (D-8).
5. Keys which render as inline markup are plain strings with a documented subset
   (`<b>`, `<br>`) rendered through one helper — not `dangerouslySetInnerHTML`
   scattered through components.

## Migration

A one-off script converts the shipped XML to the three TS modules and commits the
output. The script lives in `scripts/once/convert-locales.mjs`, is not part of the
build, and is deleted with the XML in the same commit that removes the generator.
After that:

- adding a string = adding it to all three modules in the same commit (the parity
  test is the reviewer);
- changing a string = changing three files, which is the honest cost of three
  locales;
- there is no hash baseline, no projection exception, and no generated file to
  regenerate before a commit.

## What this removes

`xml-to-ts.js` (the component that once destroyed shipped copy: D-3), the two hash
baselines, the equality hash guard and its per-attribute exceptions (which cost a
round at `fdcd731`), and the "run the generator and paste the diff" step that
appears in every copy change today.
