# 2.0.1 — login copy, plain-language rules, updates without a manual refresh

Status: superseded by 2.1.0's structure change (artifact unchanged); delivered and deployed.
Release verification is not independent acceptance.

## Scope

Three defects the owner raised after using 2.0.0:

1. the password-setup screen explained too much;
2. the password rule exposed implementation vocabulary ("Unicode code points", UTF-8 bytes);
3. the first visit after a deploy still served the previous version until a manual refresh.

The setup screen now keeps a title, one hint line ("password stays on this device and cannot be
recovered"), two password fields and one button, in all three locales. The rule reads "at least 6
characters"; error messages say "password too long" and "password contains invalid characters".
A test fails if `Unicode`, `code point`, `码点`, `码元` or `UTF-8` appears in user-visible copy.

The service worker already had `skipWaiting`, `clientsClaim` and `cleanupOutdatedCaches`; the
registration script only registered, so an old worker kept serving the cached shell. Registration
now goes through `virtual:pwa-register` with `immediate`, polls `registration.update()` every 60
seconds and when the page becomes visible, and reloads exactly once when a new worker takes
control — guarded so it cannot loop, and skipped on first install. Offline behaviour unchanged.

## Decisions

- Copy follows the app's own simple style: title, one hint, fields, button. Detail that a user
  does not need before setting a password is not shown.
- The automatic-adoption fix cannot be retroactive: a client running 2.0.0 has no update logic to
  execute, so the 2.0.0 → 2.0.1 transition may still need one manual refresh. Stated in the
  release note rather than papered over.
- Vitest files run sequentially (`fileParallelism: false`, 20 s per-test ceiling) because they
  share process-global storage state; the isolation fix is deferred with a reason.

## Verification

Gates: `eslint` 0, `tsc -b` 0, `vitest` 53 files / 577 cases (run twice consecutively after the
sequential switch), `build` 0. Production smoke in host Chromium: two password fields, one hint
line, no technical vocabulary, About showing 2.0.1, the 2.0.1 release note rendered.
The implementer's local simulation of the update path recorded one automatic reload, a correct
transition to the new bundle and a working offline navigation.

## Known limitations

- The 2.0.0 → 2.0.1 transition itself needs one manual refresh (see Decisions).
- Test isolation is unresolved; the suite is deterministic only because files run sequentially.
- Fidelity of the update path in browsers other than Chromium is untested.
- Colour contrast, Firefox and durability limits carry over from 2.0.0.
